# Rubric: is this plan ready to post and build from?

Every check grades the plan or comment against the issue, the repro
evidence, the thread, and the repo facts. None of them grades length,
headings, or polish: a terse plan that makes the decisions passes, and
a long, confident plan that is unbounded, ungrounded, or undecided
fails. `references/evidence-guide.md` says where each piece of evidence
lives; `procedure.md` says the order to gather and grade it.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-cause | The plan's stated cause (diagnosis), read against **every** step, artifact, and **control run** in the repro evidence block (live: the student's posted repro comment). | Pass if the stated cause explains the reproduced "Actual" behavior AND no control run or step in the repro evidence rules it out. A control rules a cause out when it shows the blamed component behaving correctly under the failing conditions, or shows the failure occurring with the blamed component absent or unchanged. Fail if any control contradicts the cause, if the cause blames a component the evidence never implicates while ignoring the one it isolates, or if the plan states no cause at all. A cause taken from the issue or thread still fails when the repro evidence contradicts it: the evidence outranks confident prose. | required |
| fix-targets-cause | The plan's approach, read against its own diagnosis and against the repro's Expected line. | Pass if carrying out the approach would make the reproduced failure stop at its cause, so the repro's Expected behavior would hold without a user-side workaround. Fail if the plan only documents a workaround, hides or suppresses the symptom, or changes something downstream of the cause while the reproduced behavior would still occur. | required |
| bounded-scope | The plan's in-scope list, approach steps, and named files, each item read against the single behavior the issue and repro evidence describe. | Pass if every in-scope item is needed to fix or test the reproduced behavior (the fix itself, its regression tests, and directly required plumbing). Explicitly deferring adjacent work ("not in scope", "follow-up", "separate issue") is fine and is a sign of a bounded plan. Fail if any in-scope item is work the fix does not need: a refactor or rewrite of surrounding code, a dependency upgrade or library migration, a new user-facing option/setting/UI, unrelated cleanups, CI/test-harness migrations, or fixes for other bugs, even when the core fix inside the plan is correct. | required |
| executable-approach | The plan's approach section: named files, functions, or code sites, and the chosen change at each. | Pass if a stranger could start work without asking the author anything: the plan names where the change goes (a file, function, or specific code site) AND commits to one concrete change there. A bounded, stated uncertainty about the exact line or layer ("the clamp may be one layer up; I'll confirm and say so in the PR") still passes. Fail if the location is "somewhere", the approach is "investigate/profile and see", the core decision is left open between alternatives ("X or Y, whichever is easier", "gocui? tcell? not sure"), or no file/area is named. | required |
| decisive-test-plan | The plan's test plan, read against the repro evidence's steps, Expected line, and artifact. | Pass if the test plan names at least one observable outcome specific to this fix that would differ between the broken and fixed code: the repro steps re-run with a stated expected result, or a named regression test asserting the specific behavior (exit code, output, state, count). Fail if the only verification is generic ("run the full test suite", "CI passes", "nothing else breaks", "should feel fast/correct") or names no observable outcome for the fix itself. | required |
| thread-direction | The thread highlights (live: the issue thread), especially maintainer/owner/member comments, read against the plan and the plan comment. | Pass if the thread holds no explicit maintainer direction, OR the plan comment visibly engages every piece of explicit maintainer direction: it follows it, or names it and says why it diverges. Explicit direction includes: a proposed or preferred approach, an approach the maintainer rejected, a located culprit file/line, a posted patch/test binary or request to test, and a stated constraint (performance, compatibility). Fail if the plan contradicts or ignores such direction and the comment never acknowledges it, including choosing a workaround or a different layer than the one the maintainer pointed at without saying why. | required |
| ai-disclosure | The repo-facts block's contribution policy / AI policy line (live: the repo's CONTRIBUTING and any AI policy), read against the plan comment's text. Treat every package as AI-assisted work. | First decide where the policy demands disclosure. If the policy states no AI rule, or demands disclosure only somewhere other than issue comments (e.g. "state it in the pull request") and says no disclosure is needed for issue comments, pass. If the policy demands disclosure of all AI usage, or of AI use in issues/comments, pass only if the plan comment itself discloses AI assistance (that AI was used and how/to what extent, plus the tool if the policy asks for it). Fail if that required disclosure is absent from the comment, or if the comment's own text visibly breaks another explicit comment rule in the policy (e.g. it says it was AI-generated where the policy forbids that). "Treat every package as AI-assisted" means the *work* may be AI-assisted; it never means the comment was AI-written. Take the comment's statement about its own authorship ("this comment is in my own words") at face value: that statement complies with an own-words rule, it does not violate it. | required |
| honest-unknowns | The plan's risks/unknowns/deviations text and any confident claims elsewhere in the plan, read against what the repro evidence actually shows. | Pass if the plan names at least one real risk or open question, or claims nothing the evidence leaves open. Fail if the plan states as certain something the repro evidence did not show (an untested platform, a performance claim, an unexamined second code path) without flagging it. | preferred |
| prior-art | Thread highlights for open or linked PRs, prior attempts, or other plans, read against the plan comment. | Pass if the thread names no open PR or prior attempt, or the comment acknowledges it and says how this work relates (build on it, add tests to it, or why a separate change). Fail if the comment ignores an open PR for the same fix. | preferred |

## Verdict rule

- **accept** if every `required` check grades `pass`.
- **reject** if any `required` check grades `fail` or `unclear`.
- `unclear` counts as `fail`: a plan whose readiness cannot be verified
  from the package is not ready to post and build from. Grade `unclear`
  only when the evidence the check names is genuinely absent from the
  package, never as a hedge between pass and fail.
- `preferred` checks are always graded and reported, but never change
  the verdict.
